# State machines

Most of Shelvr's state machines are implicit: a status field or a handful of
flags that several functions move by hand, with no single place that lists the
allowed transitions. This file lists them, so the next change starts from what
the machine already is. When you add a status value, a flag, a retry or a
lease, find its row here first and update it in the same change.

Paths below are under `apps/native`.

## Explicit machines

These have one pure transition function and tests per transition. Change the
transition function, not the hook around it.

## Patterns behind past bugs

- **Stale writers.** Anything that finishes later than it started (a run, a sync,
  a publish) checks it still owns the state before writing: a run id, a lease
  timestamp or a generation counter.
- **Dead ends.** A terminal failed state that nothing retries needs either a
  user-reachable retry or copy that says it stopped, not "still updating".
- **Exhausted retries.** A bounded retry loop needs another trigger, such as a
  user action or the app returning to the foreground, once its budget runs out.
- **Launch-scoped memory.** Module variables reset on a cold launch while
  SecureStore and MMKV persist. A decision kept in a module variable is
  forgotten on the next launch.
- **Idempotency keys.** An operation id names one intent. A new intent needs a
  new id, or the backend returns the earlier result for it.

## Making one explicit

Use the shape of `replay-onboarding-machine.ts`: one state object, a pure
transition per event that returns the next state and what to do, unit tests per
transition, and a hook that only runs the effects. Do it when a fix would add
another flag, or when bugs cluster in one machine. Behaviour should not change,
so the existing tests must pass untouched.

## Open questions

- A decline of the onboarding replay's own paywall is not recorded, so while
  onboarding work is queued the paywall opens again on the next run, in the
  same launch or after a cold launch. A decline at the onboarding step is kept
  only in `onboardingPaywall`, so a cold launch forgets it too. Whether a
  decline should stick is a product decision; the test "keeps the paywall open
  to a later run after a decline in the same launch" pins today's behaviour.
- A time-zone change between scheduling and relaunch may send the trial-ending
  reminder twice or not at all (`trial-reminder.ts`): it schedules from local
  hours and nothing records a delivered reminder. Not reproduced.
