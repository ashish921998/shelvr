# Account deletion

**The promise.** When someone deletes their account, the backend removes everything it stores about them. Two rows are kept on purpose (`appleTokens`, `legalConsents`), each with a job that removes it. Other accounts are untouched. Once an account has started deleting, no function adds rows for it and no notification is handed to delivery for it.

**The harm if it breaks.** A person told their account is gone still has saves, photos, push tokens or feedback in the database, gets a push naming one of their saves, or the deletion removed someone else's data.

**How it is checked.** Not a proof and not a hand-written model. The check runs the real Convex functions (vitest and convex-test, versions in `apps/native/package.json`) against every table in `schema.ts`, every function that inserts into a user-owned table (found by reading `convex/**/*.ts` with the TypeScript compiler), and every point between two passes of the batched deletion. Convex runs each mutation as one serializable transaction, so "the writer ran between drain pass k and pass k+1" is every ordering that exists for one writer. A TLA+ model of that would have to be kept in step with the code by hand, and this runs the code itself with nothing to install.

## Run it

```bash
cd apps/native && pnpm exec vitest run convex/accountDeletion.test.ts convex/notificationDelivery.test.ts convex/saveReminders.test.ts
```

A few seconds, 92 tests, 40 of them in the deletion check, all passing. The two delivery files hold the unit tests the claim checks below name. `accountDeletion.test.ts` runs in the Node environment, not `edge-runtime` like most Convex tests, because it reads source files.

Run it after any change under `apps/native/convex/`. If the change touches a file in "Covered code" at the end, also reread the policy tables at the top of the test file. It never needs a simulator, a deployment or a secret.

## Reading a failure

A failure is a finding about the code until you can show the test's model is wrong. Do not edit the policy tables to make a red test green without telling the user. One cause usually fails two to five tests that share it: read the first message, not the count.

- **`the tables › accounts for every table`**: a table has no user key and no entry in `UNOWNED_TABLES`. If it holds anything about a person, give it a `userId` and a drain step in `deleteUserOwnedDataBatch` (users.ts). If it holds nothing personal, add it to `UNOWNED_TABLES` with the reason. The "names a table that is gone / not owned" messages mean an entry is stale: delete it.
- **`leaves nothing of the account…` or `drains <table> across batches`, "a row survived"**: the drain never deletes that table, or stops early. `drains <table>` seeds 101 rows (`DELETE_BATCH + 1`), so a step that forgets to return `false` on a full batch leaves one row. Real: add or fix the step, keeping `.take(DELETE_BATCH)` and `return false` when the batch is full. If the table is meant to stay, it belongs in `RETAINED_ROWS` with the job that removes it.
- **the same tests, "a blob … survived"**: a step deletes the row but not the stored file. Real: call `safeDeleteStorage` as the items and itemOperations steps do.
- **`drains <table>` throws "unique() … more than one"**: the drain reads that table with `.unique()`, so it holds one row per account by design. Model: add the table to `ONE_ROW_PER_ACCOUNT`.
- **`leaves another account exactly as it was`**: the drain read or deleted rows it does not own, usually a query missing its `by_user` index constraint. Real.
- **`adds no row the fixture did not put there`**: deleting an account wrote a row (a log, a receipt). Decide whether it holds personal data. Real if it does.
- **`schedules the job that removes each retained row`**: `appleTokens` or `legalConsents` no longer get their removal job, or one is no longer retained. Real if the job is missing (the row would never go). Model if the row is now deleted outright: drop the `RETAINED_ROWS` entry.
- **`the writers › checks the owner before every insert…`**: names `file.ts#function`. It inserts into an owned table and neither it nor all its callers calls `liveOwner`, `requireUserId`, `aiAllowed` or a helper that does. Real: add `requireUserId(ctx)` (public) or `if ((await liveOwner(ctx, userId)) === null) return null` (internal). If a cron or scheduled job reaches the writer, also add a recipe (see "When a change is intended").
- **`the writers › keeps a recipe only for a writer that still checks the owner`**: a `RECIPES` key names a function that is gone, no longer inserts into an owned table, or lost its owner check. Real if it lost the check. Model if the function was renamed or removed: update or delete the recipe.
- **`<writer>, with an owner check › refuses a draining account at every drain pass`**: the writer wrote a row, threw, or left a row that outlived the account, at some point between two drain passes. The message lists each point ("after 1 more pass(es): wrote a row; 0 row(s) left…"). Real when it says "wrote a row": the owner check is missing, or it is called and its answer is ignored (the scan cannot see that, this test can). If many of these fail together, suspect `liveOwner` in `model/auth.ts`. A point that shows an error message ("Validator error…") means the recipe's `call` no longer matches the function: Model, fix the recipe. "the account finished deleting before there were two gaps to test" means the recipe's `padding` and `fillers` no longer keep the drain going across passes (the drain got faster, or `DELETE_BATCH` changed): Model, raise them.
- **`<writer>, then its delivery claim › hands out nothing once the account began deleting`**: `claim` or `claimReminder` accepted a digest or reminder for an account that had begun deleting, so a push naming a save can follow a confirmed deletion. Real: restore the `liveOwner` guard before the preferences read; it patches the row with `OWNER_UNAVAILABLE` and returns null.
- **`<writer>, then its delivery claim › closes what it refuses, so recovery does not queue it again`**: the claim refused the notification but left the row `pending`, so `recover` queues it again on every run, or the refusal scheduled a send or an analytics event. Real: the guard must `patch` the row with `OWNER_UNAVAILABLE` (`failed`, `owner_unavailable`, no next attempt) and return null. Do not close it with `closeBetweenAttempts`: that helper schedules a `notification_sent` event whenever the row has recipients, and marks a row `complete` once a device took the push. `notificationDelivery.test.ts` and `saveReminders.test.ts` hold the same check for an owner whose `users` row is missing, and again for a row already sent once, which is the case that has recipients.
- **`… › writes for a live account in the sweep's setup (the recipe reaches the insert)` or `… hands out what it prepared for a live account (the recipe reaches the claim)`**: the recipe no longer gets a healthy account through the writer or the claim (it gained a precondition). The first of the two runs in the sweep's own padded setup, so a recipe that could never write cannot pass the sweep for the wrong reason. Model: fix the recipe in `RECIPES` until a live account writes and is handed the notification. Until then no boundary test below it means anything.

## What the check found (fixed)

On 2026-10-22 the first run found that, for an account whose deletion takes more than one pass, a weekly shelf or save reminder could be prepared and accepted for delivery after the person confirmed deletion. Nothing was left in the database; the leak was a push naming one of their saves.

1. Someone with 110 saves taps Delete account. `deleteCurrentUserAccount` marks the user row `deleting`, deletes their oldest 100 saves and schedules the next pass with `runAfter(0)`.
2. Before that pass runs, `prepareWeeklyDigest` (or `prepareSaveReminder`), queued by the cron, runs for them. It read their `notificationPreferences` but never the owner, found enough of their newest saves still there, and wrote the digest (or reminder).
3. `claim` (`claimReminder`) accepted it: it checked preferences, devices and saves, not the owner. That is the step right before the push goes to Expo.

It happened in the other order too: a digest prepared while the account was healthy was still accepted by `claim` once deletion had started. Accounts small enough to finish in the first pass (fewer than 100 rows in any one table, fewer than 50 plan shares, under 4 MiB of saves) are deleted in the transaction that marks them and never had the window.

The fix is `if ((await liveOwner(ctx, <userId>)) === null) return null;` at the top of `prepareWeeklyDigest` and `prepareSaveReminder`. In `claim` and `claimReminder` the same check sits before the preferences read, and a refusal also closes the row: it patches it to `failed` with `owner_unavailable` and no next attempt, so `recover` never queues it again. Leaving it `pending` would have `recover` re-queue it every five minutes (50 such rows at once would fill its window), and an owner that is not a live account at all would keep it pending for good. The close is a direct patch, not `closeBetweenAttempts`, so no `notification_sent` event is scheduled for the deleting account, and a late `finish` finds the row no longer pending and does nothing. The writer recipes hold the first half and the `…then its delivery claim` tests hold the second.

## What each check covers

Sync commit: `aaaf588a` (origin/main, 2026-10-22). The check passed there with the change that added this skill applied on top (the four owner checks above with the close on refusal, and real `users` rows in the fixtures of `notificationDelivery.test.ts` and `notifications.test.ts`), and each break in "Prove it still fails" was caught there. Until the next agent moves the sync commit forward (step 6 below), the diff in "Covered code" lists `notifications.ts` and `notificationDelivery.ts`: that change is why.

- **`the tables › accounts for every table`** proves every table is owned, a child of an owned table, or explained in `UNOWNED_TABLES`. Covers `convex/schema.ts` (all tables).
- **`seeds a row in every table the account owns`** proves the fixture reaches every owned table and a blob, so the checks below cannot pass on an empty account. Covers the `schema.ts` validators.
- **`leaves nothing of the account…`, `adds no row…`, `leaves another account…`** prove that after `deleteCurrentUserAccount` and the continuation passes no row of any owned or child table, no blob and no `users` row remain except the retained rows, no extra row exists, and a second seeded account is byte-identical. Covers `users.ts` (`deleteCurrentUserAccount`, `processAccountDeletion`, `deleteAccountBatch`, `deleteUserOwnedDataBatch` and the `delete*Batch` helpers, `deleteAiConsent`, `deleteAuthIdentity`) and `planShares.ts` (`deletePlanSharesForUser`, `deleteShare`).
- **`schedules the job that removes each retained row`** proves `appleTokens` gets `appleRevoke:revoke` and `users:forgetAppleToken` (an hour later) and `legalConsents` gets `legalConsentSync:send`, each carrying the row id. The jobs are scheduled, not run. Covers `users.ts` (`scheduleAppleRevoke`), `legalConsent.ts` (`revoke`) and `model/appleTokens.ts`.
- **`drains <table> across batches`** (one per owned table except the retained and one-row tables) proves that with 101 rows of that table (other tables one row each) the drain finishes through its continuation passes and removes all of them. Covers each `.take(DELETE_BATCH)` step in `users.ts`, and `planShares.ts` (batch of 50).
- **`the writers`** prove that every function in `convex/**` (tests and `_generated` excluded) that calls `db.insert` on an owned table calls an owner check, directly or in every caller, that every writer with a recipe still does, and that no owner-check name is defined twice. Covers all of `convex/`; fences are found by name through `model/auth.ts`: `liveOwner`, `requireUserId`, and the helpers that call them.
- **The writer recipes** (`prepareWeeklyDigest`, `prepareSaveReminder`, `recordPlanVote`) prove the following. The account is padded so the drain takes several passes: 301 saves for the two notification writers, so their preferences, devices and newest saves outlive the first three gaps (the only gaps in which they can write), and 101 saves plus 101 space memberships for `recordPlanVote`. The writer runs after 0, 1, … passes until the account is gone: it writes nothing and throws nothing at any point, and no row of its table is left after the drain. The same recipe also runs once on a live account in that padded setup, so it cannot pass by never being able to write. Covers `notifications.ts`, `model/saveReminders.ts`, `model/weeklyShelf.ts`, `planShares.ts` (`liveShare`, `recordPlanVote`) and `model/auth.ts` (`liveOwner`).
- **`…then its delivery claim`** (`claim`, `claimReminder`) proves that a digest or reminder prepared for a live account is handed out, and that the same one, once the account has begun deleting, is not: the claim returns null, closes the row as `failed` (`owner_unavailable`), and no send or analytics event is scheduled, even after `recover` runs. Four unit tests prove the same for an owner whose `users` row is missing: `closes a digest whose owner is gone…` and `closes a digest already sent once when its owner is gone…` in `notificationDelivery.test.ts`, and the two matching `closes a reminder…` tests in `saveReminders.test.ts`. The "already sent once" pair is the only place a refused row has recipients, which is when `closeBetweenAttempts` would mark it `complete` and schedule `notification_sent`; the deletion check's rows are never attempted. Covers `notificationDelivery.ts`.

## Bounds and what this does not cover

- One account under test and one bystander. Rows per table: 1 each, and 101 in one table at a time. Writers are called once, at each boundary between drain passes, never two at once and never retried.
- The writer scan reads function bodies by name. It counts an owner-check call anywhere in the function, whatever is done with the answer, and it does not follow `ctx.runMutation(internal.x.y)`: a registered Convex function must carry its own check. The recipes close that gap for the three writers they cover (break `liveShare` so it ignores the answer and the scan stays green while its recipe fails). Other writers are trusted on the call alone. Only `db.insert` is scanned, not `patch` or `replace`.
- A notification already handed to the send action before the account began deleting can still reach Expo: the claim and the HTTP call cannot share a transaction. The tests cover what is claimed after deletion began, not what is in flight.
- A refused claim closes its row only when a claim reaches it: a row the drain deletes first never needs it, and a row leased to an in-flight send is skipped until the lease ends (the due check runs before the owner check).
- `finish` and `finishReminder` still schedule the PostHog `notification_sent` event when a delivery claimed before deletion began finishes while its row exists. It carries the user id (person profile off), the notification id, its kind and counts, no content.
- The writer scan reads source with the `typescript` compiler API (a dependency of `apps/native`, also used by `tools/verify-convex-api.mjs`). `the writers › finds the writers (the scan is not empty)` fails if it finds 15 or fewer.
- A table is "owned" if it has `userId` or an `id("users")` field. A table keyed another way (an email, an `ownerId` string) lands in the unexplained list on purpose.
- The Convex Auth library tables `authVerifiers` and `authRateLimits` are listed as unowned and not audited.
- Retained rows: only that their removal job is scheduled. Removal itself is covered by `appleRevoke.test.ts` ("keeps the retained token readable for the revoke job after the owner is gone, then forgets it") and `legalConsent.test.ts` ("revokes after account deletion and removes the consent record only after delivery").
- Data outside Convex is out of scope: PostHog, RevenueCat customers (beyond the consent job), Resend and delivered emails, Expo, Apple.
- The Settings > Delete account screen. The e2e suite (`tools/e2e`, see `.agents/skills/verify-shelvr`) reaches the button in `paywall.e2e.ts` but nothing taps it. Use that skill if a change touches the screen or its confirmation; this check begins at the mutation. The e2e setup is unchanged.
- A test that seeds notification rows needs a real `users` row (`ctx.db.insert("users", {})`). The owner checks treat any other id as not live, so a made-up `"user-a"` makes the function return null without writing and the test sees nothing happen.

## When a change is intended

1. Make the code change. Run the check.
2. New table with personal data: add its drain step to `deleteUserOwnedDataBatch`, and mention the table and its step in the `CLAUDE.md` schema list as `tools/verify-agent-docs.mjs` requires. If the step uses `.unique()`, add the table to `ONE_ROW_PER_ACCOUNT`. If it must outlive deletion, add it to `RETAINED_ROWS` with the job that removes it, and schedule that job in the deletion transaction.
3. New table without personal data: `UNOWNED_TABLES`, with the reason.
4. New function that inserts into an owned table: give it an owner check. If a cron, webhook or scheduled job reaches it with a raw `userId`, also add a recipe to `RECIPES`: a `fence` sentence saying what refuses a draining account, the `table` it writes, a `seed` that makes a live account write, a `call`, and the `padding` (saves) and `fillers` (rows per table) that keep the account draining across several passes while the writer's own inputs still exist. If it prepares something for delivery, add a `claim` that hands it out, and the claim tests pick it up.
5. Re-run. Then prove the edited check still fails: apply one break from the next section that touches what you changed, see the named test fail, undo it.
6. Move the sync commit above to the commit you ran against only after steps 1 to 5 hold. If code under `apps/native/convex/` changed without anyone running this, use `/maintain-formal-verification-skill`.
